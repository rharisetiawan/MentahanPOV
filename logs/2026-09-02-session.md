# Session log — 2026-09-02

Built the TikTok remote-worker feature: the HG680 hands TikTok posting
off to a second machine (the campus server) since the HG680's ARM/RAM
can't run Playwright. Full design + setup steps are in `DEPLOYMENT.md` →
"TikTok remote worker" — this is just the index of what happened and
what's left.

## What changed, in order

1. **Chose the architecture.** Considered three options: skip TikTok
   entirely, mirror the whole pipeline onto both boxes, or full
   auto-failover (campus server takes over everything if the HG680 goes
   down). Picked a middle ground — only the TikTok step moves to the
   campus server, everything else stays exactly as-is on the HG680 — after
   walking through the tradeoffs together. Confirmed: "kayake aku setuju
   dengan jalan tengah.. ayo wis gas aja..."

2. **Set up the Telegram relay channel**, since the two boxes are never
   on the same network and neither exposes a port to the internet:
   - Created a second bot, `@MentahanPOV_TikTok_bot` (token provided by
     the user), used only by the worker side.
   - Created the "MentahanPOV Jobs" Telegram group with both the main bot
     and the worker bot as members.
   - Disabled Group Privacy for the worker bot via BotFather (required —
     otherwise it only sees messages that literally @-mention it, never
     the main bot's job messages).
   - Verified end-to-end via direct Bot API `curl` calls that a message
     posted in the group is visible to the worker bot's own `getUpdates`,
     with the correct `chat_id: -5488453969`.

3. **Wrote the code:**
   - `config.py` — new fields: `tiktok_worker_group_chat_id`,
     `tiktok_worker_bot_token`, `tiktok_remote_timeout_s`.
   - `distributors/tiktok_remote.py` (new) — sends `TIKTOK_JOB <id>
     <url> <caption>` via the main bot's token, then polls
     `state/tiktok_jobs/<id>.json` locally (never Telegram) until the
     worker's result shows up or `TIKTOK_REMOTE_TIMEOUT_S` elapses.
   - `telegram_bot.py` — new `handle_tiktok_job_result()` handler,
     registered only when `TIKTOK_WORKER_GROUP_CHAT_ID` is set, watches
     that group for `TIKTOK_DONE`/`TIKTOK_FAILED` replies and writes them
     to disk for `tiktok_remote.py` to pick up.
   - `main.py` — `PLATFORM_REGISTRY["tiktok"]` now picks the local
     Playwright path or the remote-worker path automatically based on
     whether `TIKTOK_WORKER_GROUP_CHAT_ID` is configured; `tiktok` added
     to `NEEDS_POST_URL` in the remote case (the worker downloads the
     video from a URL rather than receiving raw bytes).
   - `worker_service.py` (new, lives on the campus server) — long-polls
     the group via the worker bot's token, downloads the video, calls the
     existing `distributors/tiktok.py` Playwright flow **completely
     unchanged**, replies success/failure into the group.
   - `requirements-worker.txt` (new) — lighter dependency set for the
     campus server (no Google/Gemini/Flask/python-telegram-bot, just
     `requests` + `playwright` + `python-dotenv`).
   - `.env.example` and `DEPLOYMENT.md` updated to match.

4. **Verified what could be verified without deploying:**
   - `config.py` + `distributors/tiktok_remote.py` import cleanly
     together (`python -c "import config; import distributors.tiktok_remote"`).
   - `telegram_bot.py` and `main.py` pass an AST syntax check (their full
     runtime deps — `python-telegram-bot`, `google-api-python-client` —
     aren't installed on this dev laptop, only inside the HG680's Docker
     image, so a full import check isn't possible here).
   - Committed to git (`4864c13`) but **NOT YET PUSHED** — `git push`
     needs interactive credential auth (Windows Credential Manager
     prompts on a real terminal) which isn't available from this
     automated session; run it from your own PowerShell:
     `git push origin devin/1777731695-init-mentahanpov`
