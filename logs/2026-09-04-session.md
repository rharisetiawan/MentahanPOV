## What changed, in order

1. **Diagnosed the original complaint.** User's Telegram bot chat showed
   a traceback: `google.auth.exceptions.RefreshError: invalid_grant:
   Token has been expired or revoked`. Root cause matches the known
   pattern already documented in `DEPLOYMENT.md`'s incident log — the
   Google OAuth consent screen is still in Testing mode, so refresh
   tokens die ~7 days after the original grant regardless of use.

2. **Re-authenticated Google OAuth**, following `DEPLOYMENT.md` →
   "Re-authenticating Google OAuth": ran the OAuth flow locally (real
   browser), copied the fresh `gdrive-token.json` to the HG680. Took two
   extra attempts because the first two Google accounts tried
   (`rhari.setiawan@gmail.com`, then `povmentahan@gmail.com`) didn't
   actually own the target Drive folder — confirmed by testing
   `service.files().get(fileId=GDRIVE_FOLDER_ID)` before trusting each
   token, catching the wrong-account mistake before deploying it. The
   correct account is `rhari.setiawan@unigamalang.ac.id`.

3. **Found and fixed a second, unrelated bug**: `TELEGRAM_PLATFORMS` in
   the HG680's `.env` was set to just `tiktok` — meaning every video sent
   through the Telegram bot had *only ever* attempted TikTok, silently
   skipping YouTube/Facebook/Instagram/Stories with no error (see
   `config.py`'s `telegram_platforms` field — it's a full *override* of
   `PLATFORMS` for bot-triggered runs, not an addition to it). This is
   almost certainly what the user meant by "semua sosmed saya jadi
   terhenti" — it's unclear when this got set wrong, but the effect was
   present in every job in `state/posts.json` at least back to
   2026-09-03. Fixed by changing it to
   `youtube,facebook,instagram,facebook_story,instagram_story,tiktok`.
   Confirmed fixed: a real video sent afterward posted to all platforms
   except TikTok (see next item).

4. **Found and fixed the real TikTok root cause — a design bug in the
   2026-09-02 remote-worker feature, not a config or credentials issue.**
   The Telegram-group relay (main bot posts `TIKTOK_JOB`, worker bot
   long-polls for it) never worked, in either direction, because
   **Telegram bots do not receive `message` updates for messages sent by
   other bots** — a platform-level restriction, independent of Group
   Privacy or chat membership. Confirmed by direct testing: the worker
   bot's own `getUpdates` returned nothing for a `TIKTOK_JOB` message the
   main bot posted into a group both bots were verified members of, but
   picked up the *exact same text* instantly when a human typed it
   directly. The 2026-09-02 session's own "verification" had used a
   human-typed test message, which is why it looked like it worked.

   **Fixed by replacing the whole relay** with a direct HTTP call over
   Tailscale (see item 5) — `worker_service.py` is now a small
   `ThreadingHTTPServer` exposing `POST /tiktok-job`, and
   `distributors/tiktok_remote.py` just POSTs to it and waits for the
   response in the same request. No more shared Telegram group, no
   second bot token, no local-file polling. Full design + setup steps
   rewritten in `DEPLOYMENT.md` → "TikTok remote worker".

5. **Set up Tailscale** across all three machines (this laptop, the
   HG680, and the campus server) — motivated by both the redesign above
   needing direct connectivity and by CasaOS's web terminal being
   unreliable enough this session (see "Pending" in the 2026-09-01 log,
   which already flagged this) that most of this session's diagnosis had
   to fight through it before Tailscale access was available.
   - Laptop and campus server (`msi-server`) were *already* on the same
     tailnet from a prior, undocumented setup — discovered this by
     accident (`tailscale status` on the laptop already listed
     `msi-server`), not by installing anything.
   - HG680 was not yet on the tailnet. Installed Tailscale there via a
     **Docker container** (`tailscale/tailscale`, `--net=host`,
     `NET_ADMIN`/`NET_RAW` caps) rather than a system package — needs no
     `sudo`, since `songolekor` is already in the `docker` group there
     (see item 6). Hostname `hg680-mentahanpov`, IP `100.73.125.7`.
   - Verified the *container* running `telegram_bot.py`/`main.py` (not
     just the HG680 host) can actually reach the campus server's
     Tailscale IP — this was the one part that could plausibly have
     failed (Docker's own bridge network vs. the host's Tailscale
     interface) and didn't: `docker exec ... curl
     http://100.71.198.45:8790/...` worked cleanly.

6. **Added `songolekor` to the `docker` group on both boxes** (HG680;
   campus server already had it) — `sudo docker ...` was blocking every
   single command on manual approval, and Docker socket access is
   equivalent to root anyway, so this was a net simplification, not a
   security downgrade, for a box only this user administers. Combined
   with the SSH keys already in place from 2026-09-02
   (`~/.ssh/hg680_mentahanpov`, `~/.ssh/msikampus`) plus Tailscale
   reachability, this made the rest of the session's server work fully
   scriptable — no more browser-based CasaOS terminal, no more
   per-command manual `sudo` password entry for anything Docker-related.

7. **Deployed everything to both boxes**, verified live, not just
   committed:
   - HG680: `config.py`, `main.py`, `telegram_bot.py` copied in (root
     owns `/www/apps/mentahanpov`, so copied via a throwaway root
     container rather than `sudo scp`), `.env` updated
     (`TIKTOK_WORKER_HOST=100.71.198.45`, `TIKTOK_WORKER_PORT=8790`,
     `TIKTOK_WORKER_SHARED_SECRET=<generated>`, old
     `TIKTOK_WORKER_GROUP_CHAT_ID`/`TIKTOK_WORKER_BOT_TOKEN` lines
     removed), `docker compose build mentahanpov-bot && docker compose
     up -d`.
   - Campus server: `config.py`, `worker_service.py` copied in, `.env`
     updated to match, `worker_service.py` converted from an ad-hoc
     `xvfb-run ... &` process (no supervisor, silently dead in the sense
     that it never logged past its own startup line — see below) to
     running as a **systemd `--user` unit**
     (`~/.config/systemd/user/mentahanpov-tiktok-worker.service`,
     `Restart=always`), confirmed lingering is already enabled
     (`loginctl show-user songolekor -p Linger` → `yes`) so it survives
     reboots with no one logged in.
   - Verified end-to-end: `docker exec mentahanpov-mentahanpov-bot-1`
     POSTing to the worker's real endpoint with the correct shared
     secret returned a clean, structured error for a deliberately-fake
     video URL (proving the whole request/response path works) without
     actually posting anything to TikTok.
